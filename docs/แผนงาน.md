# แผนงาน — AI Chat ตารางสอนอาจารย์ (Timetable Assistant)

**เวอร์ชัน:** 1.2 · รวมเอกสาร Spec + System Design + OCR Review เข้าเป็นแผนงานเดียว · เพิ่มโมเดล Fine-tune จาก Kaggle · **ADR-10 ตัดสินแล้ว: ยึดตามโมเดล** (โมเดลเป็นทางหลักที่ตอบ SQL tool เหลือหน้าที่สร้าง dataset + verification + fallback)
**กำหนดส่ง:** 13 กันยายน 2569 · **ทีม:** 1 คน · **เครื่อง:** โน้ตบุ๊ค RAM 8 GB ไม่มี GPU
**ขอบเขต:** 1 ภาควิชา · ~20 อาจารย์

## 1. ระบบนี้คืออะไร

เจ้าหน้าที่อัปโหลดไฟล์ตารางที่มีอยู่แล้ว (PDF จากระบบทะเบียน / รูปถ่าย / สแกน) → ระบบอ่านด้วย OCR ที่เชี่ยวชาญเอกสารไทย → แปลงเป็นข้อมูลเชิงสัมพันธ์ → นักศึกษาถามเป็นภาษาพูดผ่านแชท

**Stack:** React 18 + TypeScript · Spring Boot 4 (Java 21) · PostgreSQL 16 · Typhoon OCR 2B int8 (CPU) · **Qwen2.5-1.5B-Instruct + LoRA adapter (fine-tune บน Kaggle) เป็นตัวตอบคำถาม** · Docker Compose

> เอกสารรุ่นก่อนระบุ Spring Boot 3 แต่ Spring Initializr เลิกให้เลือกรุ่น 3.x แล้ว (เหลือ 4.0.x / 4.1.x) เพราะ 3.x หมดช่วง support แบบเปิด จึงใช้ **Boot 4.0.8** ซึ่งเป็นรุ่น 4 ที่นิ่งที่สุดในขณะเริ่มงาน จุดที่ต่างจาก Boot 3 และกระทบโค้ดจริง: starter เปลี่ยนชื่อจาก `spring-boot-starter-web` เป็น `spring-boot-starter-webmvc`, Flyway แยกเป็น `spring-boot-starter-flyway`, และ `HttpStatus.UNPROCESSABLE_ENTITY` ถูกแทนด้วย `UNPROCESSABLE_CONTENT` ตามที่ RFC 9110 เปลี่ยนคำเรียก 422

**ปัญหาที่ยากที่สุดไม่ใช่ OCR** — ในตารางจริงช่องครูมีแค่ **ชื่อต้น** ("ไมตรี", "ลจี") ไม่มีนามสกุลไม่มีรหัส ถ้าภาควิชามีครูชื่อ "ไมตรี" สองคน ระบบเดาไม่ได้และไม่ควรเดา จึงต้องมีทะเบียนครูตั้งต้น + ตาราง `teacher_alias` ให้คนจับคู่ครั้งเดียวแล้วจำถาวร

## 2. ขอบเขตงาน

| ทำใน MVP | ทำถ้าเวลาเหลือ | ไม่ทำในเฟสนี้ |
|---|---|---|
| อัปโหลดไฟล์ตาราง (PDF/รูป/Excel) | "ห้องนี้ว่างไหม" (FR-15) | แจ้งเตือนเมื่อตารางเปลี่ยน |
| OCR ตารางไทย + confidence รายฟิลด์ | เทียบตารางกลุ่มกับตารางอาจารย์หา conflict (FR-16) | ดึงข้อมูลจาก API ระบบทะเบียนตรง |
| หน้าตรวจทานเทียบรูปต้นฉบับ | ตารางลายมือ บังคับตรวจทุกช่อง (FR-17) | จัดตารางสอนให้ (scheduling) |
| จับคู่ชื่อต้น → ทะเบียนครู | "ตารางเรียนของฉันสัปดาห์นี้" | รองรับหลายคณะพร้อมกัน |
| แชทตอบ 3 คำถามหลัก + รายงานความแม่นรายฟิลด์ | | |

## 3. Workflow ข้อมูล (Raw → Ready)

ทุกไฟล์เดินผ่าน 5 ขั้นนี้เสมอ ตามลำดับ

| ขั้น | เกิดอะไร | โมเดล/เครื่องมือ | ผลลัพธ์ |
|---|---|---|---|
| **1 · Raw Data** | เก็บไฟล์ตามที่ได้รับ | — | `timetable_doc` (status=uploaded) + ไฟล์บน volume |
| **2 · Data Cleansing** | deskew / normalize contrast / ตัดขอบ, กันซ้ำด้วย sha256, แยกพิมพ์-ลายมือ, อ่านโครงตาราง | Typhoon OCR 2B int8 (VLM) | markdown ตาราง + bbox + confidence รายเซลล์ |
| **3 · Cleaned Data** | ตาราง 2 มิติที่คนอ่านออก แต่ยังไม่มี schema | — (ผลตรงจากขั้น 2) | ผลลัพธ์ OCR ต่อหน้า |
| **4 · Data Preprocessing** | Parser แปลงเป็นแถว `session`, TeacherResolver จับคู่ชื่อ, ตรวจหน่วยกิต, ส่งช่อง confidence ต่ำให้คนตรวจ | rule-based parser + alias matching + human-in-the-loop | `session`, `session_teacher`, `field_correction` |
| **5 · Ready Data** | แถวที่ผูก `teacher_id` แล้วและ publish แล้ว | LLM tool-calling ผ่าน `ScheduleQueryService` เท่านั้น | `session` (published) + `v_teacher_schedule` |

> **กฎเหล็ก:** AI แตะได้เฉพาะ **Step 5** เท่านั้น ไม่เคยเห็นไฟล์ดิบหรือ markdown จาก OCR — ทั้งตอน generate dataset ไปเทรน และตอน verification (ADR-01 ที่ยังบังคับใช้หลัง ADR-10)

## 4. สถาปัตยกรรม 4 ชั้น (RAM รวมต้องพอใน 8 GB)

| ชั้น | ส่วนประกอบ | RAM |
|---|---|---|
| **1 · Frontend** React 18 + Vite | Student Chat (มือถือ), Upload + OCR Review (จอใหญ่), Teacher Registry · REST + polling ทุก 3 วิ ไม่มี WebSocket | ~0 (static) |
| **2 · Backend** Spring Boot 4 | AuthFilter, UploadController, OcrJobWorker, ReviewController, TeacherResolver, ScheduleQueryService, ChatController, AccuracyReport | ~700 MB |
| **3 · Model sidecars** Python | `ocr-worker` (FastAPI + Typhoon OCR 2B int8, 60–120 วิ/หน้า), `pdf-text-extract` (PDFBox ใน Java), `llm` (Ollama โหลด **Qwen2.5-1.5B + LoRA merged → GGUF q4**, ~2.5 GB) | ~5.2 GB |
| **4 · Storage** | Postgres 16 (ตาราง `ocr_job` ทำหน้าที่เป็นคิวแทน message queue) + uploads volume | ~400 MB |

Java ไม่รันโมเดลเอง เรียก sidecar ผ่าน HTTP ภายใน compose network · OCR รันทีละงานเพื่อไม่แย่ง RAM กับ llm

## 5. โครงสร้างฐานข้อมูล (สรุป)

| ตาราง | บทบาท | จุดสำคัญ |
|---|---|---|
| `teacher` | ทะเบียนครู | นำเข้า CSV ครั้งแรก ถ้าไม่มี ระบบทำงานไม่ได้เลย |
| `teacher_alias` | **หัวใจของระบบ** | `unique(alias_text)` — ชื่อต้นหนึ่งชี้ครูได้คนเดียว ถ้าซ้ำต้องให้คนตัดสินก่อน |
| `subject` / `class_group` / `room` | ข้อมูลอ้างอิง | ท/ป/น/ช อ่านจากตารางส่วนหัว ใช้ตรวจความสอดคล้องจำนวนคาบ |
| `timetable_doc` | ไฟล์ต้นฉบับ | `sha256` unique กันอัปซ้ำ · ลบไฟล์ตาม PDPA ได้โดยข้อมูลตารางยังอยู่ |
| `ocr_job` | คิวงาน | `SELECT ... FOR UPDATE SKIP LOCKED` + `@Scheduled` poll ทุก 5 วิ |
| `session` | แกนกลาง (คาบเรียน) | `conf` jsonb รายฟิลด์ · `bbox` jsonb ชี้กรอบบนรูปต้นฉบับ |
| `session_teacher` | ครูสอนร่วม | `teacher_id` เป็น null ได้ระหว่างยังไม่จับคู่ |
| `field_correction` | ที่มาของตัวเลข % ทุกตัวในรายงาน | ทุกครั้งที่คนแก้ = ground truth หนึ่งจุด |
| `v_teacher_schedule` | **view ไม่ใช่ตาราง** | derive จาก `session JOIN session_teacher` → ตารางกลุ่มกับตารางอาจารย์ไม่มีทางไม่ตรงกัน |
| `app_user` / `chat_message` | ผู้ใช้ + บทสนทนา | เก็บ `tool_calls` และ `latency_ms` ไว้ตอบกรรมการว่าตอบจากข้อมูลไหน ใช้เวลาเท่าไร |

## 6. REST API

### 6.1 ข้อตกลงร่วมของทุก endpoint

| หัวข้อ | กติกา |
|---|---|
| Base path | `/api/v1/...` — ใส่เวอร์ชันตั้งแต่ต้น เพราะ contract ของ `POST /chat` จะเปลี่ยนแน่เมื่อโมเดลเปลี่ยนรุ่น |
| Auth | `Authorization: Bearer <token>` จาก SSO ทุก endpoint · บทบาท `student` / `staff` / `teacher` · ไม่มี token = `401`, บทบาทไม่พอ = `403` |
| Content type | `application/json; charset=utf-8` ยกเว้น upload (`multipart/form-data`) และรูป (`image/jpeg`) |
| รูปแบบ error | RFC 9457 `application/problem+json` เหมือนกันทุกตัว ไม่มี endpoint ไหนคืน error รูปแบบอื่น |
| ตัวระบุ | id เป็น `bigserial` ในระบบ แต่ resource ที่มีรหัสตามธรรมชาติใช้รหัสนั้นเป็น path (`/subjects/31900-1003`, `/rooms/COM404`) |
| เวลา/วันที่ | ISO 8601 · ฟิลด์เวลาลงท้าย `At` เสมอ (`uploadedAt`, `trainedAt`) · วันที่ปฏิทินไทยส่งเป็น string `"2569-09-08"` ตามที่ผู้ใช้เห็น |
| Idempotency | `POST` ที่สร้างของหนักให้ส่ง header `Idempotency-Key` ได้ (`/docs`, `/model/trainings`) ส่งซ้ำด้วยคีย์เดิมคืนผลเดิม ไม่สร้างงานใหม่ |
| Pagination | รายการยาวใช้ `?limit=&cursor=` คืน `{ items, nextCursor }` ไม่ใช้ offset (ข้อมูลแทรกระหว่างหน้าแล้วเลื่อน) |
| ตั้งชื่อ | คำนาม พหูพจน์ ตัวเล็ก (`/docs`, `/sessions`, `/aliases`) · กริยาอยู่ที่ HTTP method · ยกเว้นการกระทำที่ไม่ใช่ CRUD ใช้ sub-resource (`/docs/{id}/publish`, `/jobs/{id}/retry`) |
| Status code | `200` สำเร็จ · `201` สร้างแล้ว + `Location` · `202` รับเข้าคิว · `204` ลบแล้ว · `409` ชนกับสถานะปัจจุบัน · `422` ข้อมูลถูกรูปแบบแต่ทำไม่ได้ตามกฎธุรกิจ |

**รูปแบบ error กลาง**
```json
{ "type": "https://timetable.local/errors/alias-conflict",
  "title": "ชื่อต้นนี้ผูกกับครูคนอื่นแล้ว",
  "status": 409,
  "detail": "alias \"ไมตรี\" ผูกกับ teacherId=14 อยู่แล้ว",
  "instance": "/api/v1/aliases",
  "errors": [{ "field": "aliasText", "message": "ต้องยืนยันทับก่อน" }] }
```

### 6.2 Step 1–2 · อัปโหลดและงาน OCR

| Method | Path | Role | หน้าที่ | I/O |
|---|---|---|---|---|
| `POST` | `/docs` | staff | อัปโหลดไฟล์ เข้าคิว OCR (หรือทางด่วน PDFBox ถ้ามี text layer) | multipart: `file`, `kind=class_group\|teacher`, `semester`, `weekFrom`, `weekTo`, `handwritten`<br>`201` → `{ docId, jobId, state:"queued", engine:"typhoon", duplicate:false }` |
| `GET` | `/jobs/{jobId}` | staff | สถานะงาน — React poll ทุก 3 วิ | `200` → `{ state:"running", pageDone:1, pageTotal:3, flagged:14, etaSec:120 }` |
| `POST` | `/jobs/{jobId}/retry` | staff | รันงานที่ `failed` ใหม่ (รีเซ็ต attempts) | `202` → `{ state:"queued" }` · `409` ถ้างานยังไม่ failed |
| `GET` | `/docs/{docId}/image` | ทุกบทบาท | รูปต้นฉบับสำหรับหน้าตรวจทานและลิงก์ "ดูที่มา" | `200` → `image/jpeg` (stream จาก volume) |
| `DELETE` | `/docs/{docId}/file` | staff | ลบไฟล์ต้นฉบับตาม PDPA โดยข้อมูลตารางยังอยู่ | `204` |

### 6.3 Step 3–4 · ตรวจทานผล OCR

| Method | Path | Role | หน้าที่ | I/O |
|---|---|---|---|---|
| `GET` | `/docs/{docId}/sessions` | staff | คาบทั้งหมดที่สกัดได้ + confidence + bbox + ครูผู้สอน | `200` → `{ header:{ groupCode, groupName, semester, weekFrom, weekTo, advisor }, sessions:[{ id, day, periodStart, periodSpan, kind, subjectCode, roomCode, conf:{...}, bbox:{...}, teachers:[{ ordinal, aliasText, teacherId, confidence, candidates:[{ id, label }] }] }] }` |
| `PATCH` | `/sessions/{id}` | staff | แก้ค่าในคาบ รวมย้ายวัน/คาบ/ขยายคาบ — บันทึก `field_correction` อัตโนมัติ | `{ subjectCode?, roomCode?, day?, periodStart?, periodSpan?, kind?, weekFrom?, weekTo? }`<br>`200` → `{ session, correctionsLogged:2 }` |
| `PUT` | `/sessions/{id}/teachers` | staff | กำหนดครูผู้สอนทั้งชุดของคาบนั้น (รองรับสอนร่วม) | `{ teachers:[{ ordinal:1, aliasText:"สายชล", teacherId:3 }, { ordinal:2, aliasText:"ธัญญาเรศ", teacherId:30 }] }`<br>`200` → `{ session }` |
| `POST` | `/aliases` | staff | ผูกชื่อต้นกับตัวครูถาวร — ครั้งเดียวใช้ได้ทุกไฟล์ต่อจากนี้ | `{ aliasText:"ไมตรี", teacherId:14, sourceDocId:7 }`<br>`201` → `{ aliasId, appliedToSessions:9 }` · `409` ชื่อนี้ผูกครูคนอื่นแล้ว |
| `POST` | `/docs/{docId}/publish` | staff | ทำให้ตารางตอบคำถามได้ (ลายมือต้องตรวจครบ 100%) | `200` → `{ status:"published", unreviewedCells:6 }` · `422` ลายมือยังตรวจไม่ครบ |

> **สัญญาณสำคัญ:** `publish` สำเร็จ = Ready Data เปลี่ยน → ระบบตั้งธง `datasetStale=true` ให้ pipeline โมเดล (ดู 6.5)

### 6.4 Step 5 · แชทและการค้นตาราง

| Method | Path | Role | หน้าที่ | I/O |
|---|---|---|---|---|
| `POST` | `/chat` | ทุกบทบาท | ถามภาษาไทย — โมเดล fine-tune ตอบ (ดู 8.5) | `{ conversationId, text:"อ.ไมตรี พรุ่งนี้สอนอะไร" }`<br>`200` → ดูตัวอย่างด้านล่าง |
| `GET` | `/teachers/{id}/schedule` | ทุกบทบาท | ตารางสอนของอาจารย์ (อ่านจาก view) | `?date=2569-09-08` หรือ `?week=6`<br>`200` → `{ teacher, sessions:[...], derivedFromGroups:12, completeness:"partial" }` |
| `GET` | `/teachers/{id}/free` | ทุกบทบาท | ช่วงเวลาที่ไม่มีคาบสอน | `?date=2569-09-08`<br>`200` → `{ free:[{ periodStart:3, periodSpan:2, time:"10:00-12:00" }], warning:"คำนวณจากตาราง 12 กลุ่มที่มีในระบบ" }` |
| `GET` | `/subjects/{code}/sessions` | ทุกบทบาท | วิชานี้เรียนที่ไหน เวลาไหน ใครสอน | `200` → `{ subject, sessions:[...] }` |
| `GET` | `/rooms/{code}/availability` | ทุกบทบาท | ห้องนี้ว่างช่วงไหน | `?date=2569-09-08`<br>`200` → `{ occupied:[...], free:[...], roomVerified:true }` |

**`POST /api/v1/chat` — response contract เต็ม**
```json
{ "conversationId": "3f1c...",
  "answer": "อ.ไมตรี วันอังคารสอน 2 คาบ ...",
  "source": "model",
  "modelVersion": "adapter-2569w37-r3",
  "trainedAt": "2569-09-11T18:20:00+07:00",
  "dataSnapshot": { "semester": "1/2569", "publishedDocs": 12, "builtAt": "2569-09-11T17:40:00+07:00" },
  "verification": { "checked": true, "passed": true, "mismatchedFields": [] },
  "confidence": "unverified",
  "citations": [{ "sessionId": 812, "docId": 7, "conf": 0.62 }],
  "clarify": null,
  "latencyMs": 1840 }
```

| ฟิลด์ | ทำไมต้องมี |
|---|---|
| `source` | `model` / `tool` / `template` — บอกว่าคำตอบนี้มาจากทางไหน ต้องตอบกรรมการได้ทุกข้อความ |
| `modelVersion` + `trainedAt` | เมื่อคำตอบมาจาก weight ต้องรู้ว่าเป็น weight รุ่นไหน ไม่งั้นย้อนรอยคำตอบผิดไม่ได้ |
| `dataSnapshot` | บอกว่า weight นี้เรียนจาก Ready Data ณ เวลาใด กี่เอกสาร — แทนที่ "แถวไหน" ที่ระบบแบบ SQL เคยให้ |
| `verification` | ผลการเทียบคำตอบกับ SQL จริง (6.5) — `passed:false` แปลว่าระบบทิ้งคำตอบโมเดลแล้วใช้ tool/template แทน |
| `clarify` | ชื่อกำกวม → `{ question:"หมายถึงคนไหน", options:[{ teacherId, label }] }` ห้ามเดา |

### 6.5 โมเดลและ pipeline เทรน (เพิ่มใหม่ตาม ADR-10)

| Method | Path | Role | หน้าที่ | I/O |
|---|---|---|---|---|
| `GET` | `/model/versions` | staff · teacher | รายการ adapter ทุกรุ่น รุ่นไหน active | `200` → `{ items:[{ id:"adapter-2569w37-r3", active:true, baseModel:"Qwen/Qwen2.5-1.5B-Instruct", trainedAt, datasetSize:1853, chrf:78.4, exactMatch:0.42, dataSnapshot:{...} }], nextCursor:null }` |

## 7. ชั้น SQL tool (บทบาทเปลี่ยนตาม ADR-10)

`teacherDay(teacherName, date)` · `subjectWhere(subjectQuery, semester?)` · `teacherFree(teacherName, date)` · `groupWeek(classGroupCode, week)` · `roomFree(roomCode, date)` · `whoTeaches(subjectQuery)`

ข้างในเป็น SQL parameterized ที่เขียนไว้ล่วงหน้าเหมือนเดิม — แต่หลังจากยึดตามโมเดลแล้ว ชั้นนี้ทำ **3 หน้าที่** แทนการเป็นทางเดียวที่ตอบได้

1. **สร้าง dataset** — `POST /model/datasets` generate คู่ Q&A จากผล SQL เหล่านี้ ฉะนั้นทุกคำตอบที่โมเดลเรียนมาจากข้อมูลจริงในฐาน ไม่มีการแต่ง
2. **ตรวจคำตอบ (verification)** — คำตอบจากโมเดลถูกถอดตัวเลข/รหัสวิชา/ห้อง/เวลา แล้วเทียบกับผล SQL จริง ไม่ตรง = `verification.passed:false` ทิ้งคำตอบแล้ว fallback
3. **fallback + คำถามนอก scope** — คำถามที่ dataset ไม่เคยครอบคลุม หรือข้อมูลเพิ่งเปลี่ยนหลังเทรน ให้ตอบจาก SQL ตรง ๆ (`source:"tool"`)

**กฎบังคับของชั้นแชท (ฉบับแก้ตาม ADR-10)**
1. คำตอบทุกข้อความต้องบอก `source` และถ้าเป็น `model` ต้องบอก `modelVersion` + `dataSnapshot` — ห้ามมีคำตอบที่บอกไม่ได้ว่ามาจากไหน
2. ตัวเลข วัน ห้อง รหัสวิชา ที่โมเดลพูดออกมา ต้องผ่าน verification เทียบ SQL ก่อนส่งออกเสมอ
3. verification ไม่ผ่าน → ทิ้งคำตอบโมเดล ใช้ tool/template แทน และนับเข้า `fallbackRate`
4. ชื่อต้นที่ชี้ครูได้หลายคน ต้องถามกลับ ห้ามเดา (ยังคงเดิม)
5. ข้อมูลที่ยังไม่ตรวจทานตอบได้ แต่ต้องติดป้ายความมั่นใจ + ลิงก์รูปต้นฉบับ (ยังคงเดิม)
6. `stale:true` (Ready Data เปลี่ยนหลังเทรน) → หน้าแชทขึ้นแถบเตือน และคำถามที่แตะเอกสารที่เพิ่ง publish บังคับใช้ tool path

## 8. โมเดล Fine-tune จาก Kaggle (ส่วนที่เพิ่มใหม่)

### 8.1 โมเดลนี้คืออะไร

โมเดลที่ผ่านการ **Fine-tune ให้เป็น Chatbot ตอบคำถามเกี่ยวกับ "ตารางสอนอาจารย์"** โดยใช้โมเดลพื้นฐาน `Qwen/Qwen2.5-1.5B-Instruct` แล้วใช้ **LoRA (Low-Rank Adaptation)** ฝึกเพิ่มเฉพาะส่วนเล็ก ๆ ของโมเดล (Adapter) — **ไม่ได้สร้าง AI ใหม่จากศูนย์** และไม่ได้ทำ Full Fine-tuning

สร้างมาเพื่อ Fine-tune Qwen ให้ตอบคำถามเกี่ยวกับ **ตารางสอนอาจารย์ที่มีอยู่แล้ว** ในรูปแบบ Chatbot โดยใช้ Q&A Dataset + LoRA

### 8.2 ข้อมูลที่ใช้เทรน

| ชุด | จำนวน | ไฟล์ |
|---|---|---|
| Train | 1,668 คู่ | `dataset/schedule_chatbot_train.jsonl` |
| Validation | 185 คู่ | `dataset/schedule_chatbot_validation.jsonl` |
| Test | — (ยังไม่มี) | ขั้นทดสอบใช้ validation แทนอัตโนมัติ |

schema ต่อ record: `instruction` / `question` / `answer` — ตรวจ schema ตั้งแต่ตอนโหลด ถ้า record ขาด key จะ error พร้อมบอก index
ทุกคำตอบมาจากข้อมูลจริงในไฟล์ JSON ต้นฉบับ ไม่มีการแต่งเติม

**ตัวอย่าง**
```json
{"instruction":"ตอบคำถามเกี่ยวกับตารางสอนของอาจารย์จากข้อมูลที่กำหนด",
 "question":"วันอังคารคาบแรกเวลาอะไร",
 "answer":"วันอังคาร เริ่มสอนคาบแรกเวลา 10:00 คือวิชาการสร้างสื่อดิจิทัล (31900-1003) ห้อง COM404 กลุ่ม สท.4/1"}
```

### 8.3 ค่าที่ใช้เทรน (notebook: `notebook2d9739102c.ipynb`)

| หัวข้อ | ค่า |
|---|---|
| Base model | `Qwen/Qwen2.5-1.5B-Instruct` (สลับเป็น 3B หรือ `scb10x/llama3.1-typhoon2-8b-instruct` ได้ใน Cell ตั้งค่า) |
| เทคนิค | LoRA · r=16 · alpha=32 · dropout=0.05 · bias=none |
| target_modules | `q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj` (attention + MLP) |
| Quantization | 4bit nf4 + double quant เปิดอัตโนมัติเมื่อเจอ CUDA GPU |
| Framework | HuggingFace `transformers` + `peft` + `trl` (SFTTrainer) |
| Epochs / batch | 3 epoch · batch 2 × grad accum 4 = effective 8 (~200 steps/epoch) |
| LR / scheduler | 2e-4 · cosine · warmup_ratio 0.05 · weight_decay 0.01 |
| dtype | bf16 บน Ampere ขึ้นไป, fp16 บน T4 (Turing ไม่มี bf16 ในฮาร์ดแวร์) |
| max_length / packing | 768 · packing=False · `completion_only_loss=True` (คิด loss เฉพาะส่วนคำตอบ) |
| Early stopping | patience=2 บน `eval_loss` + `load_best_model_at_end` |
| รูปแบบข้อมูล | Chat template ของโมเดล: system=instruction, user=question, assistant=answer |
| ผลลัพธ์ | LoRA adapter ที่ `/kaggle/working/lora_adapter_schedule_chatbot` (+ `.zip`) · merge เข้า base ได้ถ้าตั้ง `MERGE_MODEL=True` และปิด 4bit |
| สภาพแวดล้อม | Kaggle/Colab GPU (T4 16GB ก็พอ) · ต้องมีอินเทอร์เน็ตโหลดโมเดลฐาน |

### 8.4 การวัดผล

วัดด้วย **chrF** (0–100 เทียบ n-gram ระดับตัวอักษร) + **exact match** — **ไม่ใช้ ROUGE** เพราะ ROUGE ตัดคำด้วยช่องว่าง ส่วนภาษาไทยเขียนติดกัน ทำให้คะแนนต่ำผิดปกติแม้ตอบถูก
ประเมิน 20 รายการจากชุดที่โมเดลไม่ได้เทรน และพิมพ์เฉพาะเคสที่ตอบไม่ตรง เพื่อแยกว่าพลาดรายละเอียดหรือผิดข้อเท็จจริง

### 8.5 โมเดลนี้วางตรงไหนในระบบ (ADR-10)

> **ADR-10 · สถานะ: ตัดสินแล้ว** — **ยึดตามโมเดล** · LoRA fine-tuned Qwen2.5-1.5B เป็น **ทางหลักที่ตอบคำถามผู้ใช้** ส่วน SQL tool ลดบทบาทลงเป็นแหล่งสร้าง dataset + ตัวตรวจคำตอบ + fallback

**สิ่งที่เปลี่ยนจาก ADR-01/ADR-04:** เดิมกำหนดว่า AI ห้ามตอบจากความรู้ในตัวโมเดล ตอนนี้แก้เป็น — โมเดลตอบจาก weight ได้ แต่คำตอบต้องผ่าน verification เทียบ SQL ก่อนออกเสมอ ADR-01 ยังคงอยู่ในส่วนที่ว่า **ไม่ทำ RAG บนข้อความ OCR ดิบ** (ข้อมูลที่โมเดลเรียนมาจาก Ready Data ที่ผ่าน parser + คนตรวจแล้วเท่านั้น) ส่วน ADR-04 ถูกแทนที่ทั้งข้อ

**เส้นทางคำตอบใหม่**

```
คำถาม → [1] โมเดล fine-tune ตอบ (source="model")
            ↓
        [2] Verification: ถอดตัวเลข/วัน/ห้อง/รหัสวิชา จากคำตอบ → เทียบ SQL จริง
            ↓ ผ่าน                         ↓ ไม่ผ่าน / stale / นอก scope
        ส่งคำตอบ + modelVersion       [3] fallback: SQL tool (source="tool")
        + dataSnapshot + citations         หรือ template (source="template")
```

**ทำไมยึดตามโมเดลได้:** dataset ทุกคู่ถูก generate จาก Ready Data ที่ผ่าน parser และคนตรวจทานแล้ว (ข้อ 8.2 — "ทุกคำตอบมาจากข้อมูลจริงในไฟล์ JSON ต้นฉบับ") ไม่ใช่ข้อความ OCR ดิบและไม่ใช่ความรู้ทั่วไปของโมเดล ฉะนั้นสิ่งที่อยู่ใน weight คือตารางจริงของภาควิชา ไม่ใช่การเดา · ได้สำนวนไทยลื่นกว่า ตอบเร็วกว่าเพราะไม่ต้องรอ tool round-trip และคำถามที่รูปประโยคแปลกก็ยังตอบได้โดยไม่ต้องพึ่ง LLM เลือก tool ถูก

**ราคาที่จ่าย (ต้องเขียนในเล่มและตอบกรรมการให้ได้)**

| ปัญหา | วิธีคุม |
|---|---|
| ตารางเปลี่ยนแล้ว weight ไม่รู้ | `GET /model/staleness` + ธง `datasetStale` ตอน publish · `stale:true` = ขึ้นแถบเตือนบนหน้าแชท และคำถามที่แตะเอกสารใหม่บังคับใช้ tool path |
| ตรวจย้อนไม่ได้ว่าคำตอบมาจากแถวไหน | ทุก response แนบ `modelVersion` + `trainedAt` + `dataSnapshot` (เทรนจาก Ready Data ณ เวลาใด กี่เอกสาร) และ verification แนบ `citations` กลับมาให้ |
| โมเดลตอบผิดแบบมั่นใจ (hallucination) | verification บังคับ 100% ของคำตอบ ไม่ใช่สุ่มตรวจ · ไม่ผ่าน = ทิ้งทันที นับเข้า `fallbackRate` ใน `/reports/chat-quality` |
| ต้องเทรนใหม่ทุกครั้งที่ตารางเปลี่ยน | pipeline สั่งได้จาก API: `POST /model/datasets` → export `.jsonl` → เทรนบน Kaggle → `POST /model/versions` อัปกลับ → `activate` · rollback ด้วย `activate` รุ่นเก่าได้ทันที |
| adapter รุ่นใหม่แย่กว่าเดิม | `activate` บล็อกด้วย `422` ถ้า chrF ต่ำกว่าเกณฑ์ของรุ่นที่ใช้อยู่ |
| deploy บนเครื่อง 8 GB | merge adapter → แปลง GGUF q4 → ให้ Ollama โหลด ใช้ช่อง RAM เดิมของ llm sidecar (~2.5 GB) ไม่เพิ่ม service ใหม่ |

**ทางเลือกที่ไม่เลือก:** ให้โมเดลทำแค่เลือก tool + เรียบเรียงผล SQL (ADR-04 เดิม) — ตรวจย้อนได้ง่ายกว่าและไม่ต้องเทรนใหม่เมื่อตารางเปลี่ยน แต่สำนวนไทยแข็ง คำถามซับซ้อนเลือก tool ผิด และไม่ได้ใช้ประโยชน์จากโมเดลที่เทรนไว้แล้ว

### 8.6 ข้อจำกัดที่ต้องเขียนในเล่ม

- Dataset ~1.8 พันคู่ และเนื้อหาซ้ำแนวกันสูง → คำถามที่รูปประโยคหลุดจากแนวที่เทรนจะตอบได้ไม่ดี · เมื่อยึดตามโมเดลแล้ว ข้อนี้กระทบผู้ใช้โดยตรง จึงต้องพึ่ง verification + fallback เป็นตาข่าย และต้องเพิ่มความหลากหลายของคำถามในรอบถัดไปเป็นงานอันดับแรก
- ยังไม่มีชุด test แยก ตัวเลขจาก validation จึงเป็นค่าอ้างอิงคร่าว ๆ — dataset builder รอบใหม่ (BE-13) ต้องแยก test ตั้งแต่ตอน generate
- โมเดลรู้ตารางเท่าที่ Ready Data มี ณ วันเทรน ไม่ใช่ ณ วันที่ถาม — `/model/staleness` คือสิ่งที่ปิดช่องนี้ ไม่ใช่ตัวโมเดล

| ADR-07 | ตัดสินแล้ว | publish อัตโนมัติ + ป้ายความมั่นใจ ไม่บล็อกรอคนตรวจ | นักศึกษาอาจเห็นข้อมูลผิดก่อนถูกแก้ จึงต้องมีป้าย + ลิงก์รูปทุกครั้ง |
| ADR-08 | ตัดสินแล้ว | ตารางเขียนด้วยมือไม่ publish อัตโนมัติ บังคับตรวจทุกช่อง | เจ้าหน้าที่ทำงานมากขึ้นกับไฟล์กลุ่มนี้ |
| ADR-09 | ความเสี่ยงที่เหลือ | ยังไม่มีข้อมูลจริงและ ground truth → สร้าง eval set เองจากตารางอาชีวะ/เทคนิคสาธารณะ | ไม่ทำใน 2 วันแรก = ไม่มีตัวเลข % ให้อาจารย์วันส่ง |
| **ADR-10** | **ตัดสินแล้ว** | **ยึดตามโมเดล — LoRA fine-tuned Qwen2.5-1.5B เป็นทางหลักที่ตอบคำถาม · SQL tool เหลือหน้าที่สร้าง dataset + verification + fallback** (ดูข้อ 8.5) | ตารางเปลี่ยนต้องเทรนใหม่ · ตรวจย้อนได้แค่ระดับ snapshot ไม่ใช่ระดับแถว · ต้องมี verification 100% ของคำตอบ |

## 10. เกณฑ์วัดความแม่นของ OCR

วัดแบบ **field accuracy** แยกรายฟิลด์ คำนวณจากตาราง `field_correction` ตรง ๆ ไม่ต้องทำ dataset แยก

```
field_accuracy(f) = COUNT(ocr_value = human_value WHERE field = f) / COUNT(* WHERE field = f)
```

| ฟิลด์ | เป้า | ขั้นต่ำ | เหตุผล |
|---|---|---|---|
| รหัสวิชา | ≥ 98% | 95% | ตัวเลขล้วน และเป็นกุญแจเชื่อมไปตารางวิชา |
| ห้องเรียน | ≥ 95% | 90% | ผสมอังกฤษ-เลข-ไทย เขียนตัวเล็กในช่องแคบ |
| วัน/คาบ/จำนวนคาบ | ≥ 97% | 93% | อนุมานจากตำแหน่งเซลล์ พลาดเมื่อรูปเอียงหรือเส้นขาด |
| ชื่อครู | ≥ 90% | 85% | **จุดอ่อนที่สุด** — ไทย ย่อเหลือชื่อต้น บางช่องมีสองชื่อ |
| หน่วยกิต (ท ป น ช) | ≥ 92% | 85% | ตัวเล็กมากในส่วนหัว แต่ไม่กระทบคำตอบหลัก |
| ตารางลายมือ | ไม่กำหนด | — | CER ลายมือไทย 20–75% รายงานตัวเลขจริงและบังคับคนตรวจ |

**ชุดข้อมูลทดสอบ 20 หน้า** (ต้องเสร็จภายใน 9 ก.ย. — ข้ามขั้นนี้ = วันสอบไม่มีผลการทดลอง): PDF มี text layer 4 · PDF สแกนคม 4 · รูปถ่ายเอียง/มีเงา 6 · ลายมือ 2 · ฟอร์แมตแปลก 4 · พิมพ์คำตอบที่ถูกด้วยมือเป็น JSON เทียบ

## 13. แบ่งงานเป็น Pipeline ย่อย

**Frontend:** FE-1 Auth guard · FE-2 ฟอร์มอัปโหลด · FE-3 Job status poller · FE-4 หน้าตรวจทาน split view · FE-5 หน้าแชท · FE-6 ทะเบียนครู + รายงาน
**Backend:** BE-1 UploadController · BE-2 ทางด่วน PDFBox · BE-3 OcrJobWorker · BE-4 Parser · BE-5 TeacherResolver · BE-6 ReviewController · BE-7 บันทึกการแก้ไข · BE-8 Publish gate · BE-9 ChatController · **BE-10 Verification (เทียบคำตอบโมเดลกับ SQL)** · BE-11 import CSV · BE-12 AccuracyReport · **BE-13 DatasetBuilder (Ready Data → Q&A jsonl)** · **BE-14 ModelRegistry (version / activate / staleness)**
**DB (Flyway):** DB-1 baseline · DB-2 doc+job · DB-3 session · DB-4 field_correction · DB-5 view · DB-6 ดัชนี · **DB-7 model_version, model_dataset (เก็บ metric + snapshot)**
**ML sidecar:** ML-1 Preprocess · ML-2 Typhoon OCR inference · **ML-3 LoRA adapter inference (`POST /infer`) — ทางหลักที่ตอบ** · ML-4 SQL tool fallback + template

**สายอัปโหลด → ใช้งานได้**
`FE-2 → BE-1 → BE-2 (ถ้ามี text layer จบสาย) หรือ BE-3 → ML-1 → ML-2 → BE-4 → BE-5 → FE-3 (poll) → FE-4 → BE-6 → BE-7 → BE-8 → publish`

**สายนักศึกษาถาม → ได้คำตอบ (ตาม ADR-10)**
`FE-5 → BE-9 → ML-3 (adapter ตอบ) → BE-10 verification เทียบ DB-5/session → ผ่าน: FE-5 (+ modelVersion, dataSnapshot, citations) / ไม่ผ่าน: ML-4 SQL tool หรือ template → FE-5`

**สายเทรนโมเดลรอบใหม่ (วนซ้ำทุกครั้งที่ Ready Data เปลี่ยนมาก)**
`BE-8 publish → datasetStale → BE-13 generate jsonl → export → Kaggle (LoRA) → POST /model/versions → BE-14 activate → ML-3 โหลด adapter รุ่นใหม่`

## 15. คำถามที่ยังไม่มีคำตอบ

1. **ทะเบียนครูของภาควิชา** — ยังไม่มีไฟล์รายชื่อจริง ถ้าไม่ได้ก่อน 10 ก.ย. จะสาธิตด้วยข้อมูลสมมติ ซึ่งลดน้ำหนักผลการทดลอง
2. **จำนวนกลุ่มเรียนจริง** — มีผลต่อคำถาม "อาจารย์ว่างช่วงไหน" ถ้าอัปไม่ครบต้องแสดงคำเตือนว่าข้อมูลอาจไม่สมบูรณ์
3. **SSO ของมหาวิทยาลัย** — ยังไม่ทราบว่าเปิด OIDC ให้โปรเจกต์นักศึกษาหรือไม่
4. **รายการห้องเรียนทั้งหมด** — "ห้องนี้ว่างไหม" ตอบถูกเฉพาะเมื่อมีผังห้องครบ
5. **ความถี่การเทรนใหม่** — ADR-10 ตัดสินแล้วว่ายึดตามโมเดล เหลือคำถามว่าจะเทรนใหม่ทุกครั้งที่ publish หรือรอให้ `staleness` ถึงเกณฑ์ (เช่น เอกสารใหม่ ≥ 3 ฉบับ) · ระหว่างรอ ให้ fallback เป็น tool path ไปก่อน
6. **เกณฑ์ chrF ขั้นต่ำสำหรับ `activate`** — ยังไม่มีตัวเลขอ้างอิง ต้องรอผลเทรนรอบแรกจากข้อมูลจริงก่อนตั้งเกณฑ์
